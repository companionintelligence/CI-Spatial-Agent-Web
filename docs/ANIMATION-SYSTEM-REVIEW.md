finding put through an adversarial verifier that defaults to refuting it against the live code.
**59 findings survived** (1 refuted). Severity: critical = app-visibly broken; high = wrong

## CRITICAL (2)

### C1. Barge-in during TTS playback corrupts nextExpectedId, permanently silencing all subsequent speech until another barge-in

- **Where:** `packages/core/src/services/tts/ttsService.ts:375` · llm-reaction-integration · state-machine · **CONFIRMED**
- **Mechanism:** stopSpeaking (ttsService.ts:438-457) clears messageQueue, sets nextExpectedId.current = globalId and isProcessing.current = false — but the in-flight processQueue loop is still awaiting playAudioBuffer (ttsService.ts:366) and has no way to be cancelled. When the old audio finally ends, the zombie loop resumes and executes `nextExpectedId.current = nextMessage.id + 1` (ttsService.ts:375), rolling the expected id BACKWARDS past the reset. processQueue only plays a message whose id exactly equals nextExpectedId (ttsService.ts:274), and nothing else ever advances it, so every message queued afterwards (ids >= the globalId snapshot) never matches: the loop breaks immediately (ttsService.ts:279) and the messages sit stranded forever. Additionally, because stopSpeaking sets isProcessing=false while the zombie loop is still alive, a new speak() call (ttsService.ts:429-431) starts a SECOND concurrent processQueue, so old and new audio can play simultaneously. Only another stopSpeaking (which re-snapshots globalId) unwedges the id counter — and the stranded messages leak in messageQueue, keeping audioQueue non-zero.
- **Fails when:** Voice conversation, default config (bargeInEnabled=true, tts mode 'pocket'/'remote'): avatar is speaking, user says 'stop'. shouldTriggerBargeIn fires, stopSpeaking runs while playAudioBuffer is awaiting. The current utterance finishes, the zombie loop rolls nextExpectedId back. User asks the next question — the LLM answers in the chat overlay but the avatar is completely mute (no TTS, no lip-sync) for every subsequent response, until the user happens to trigger barge-in again.
- **Verifier correction:** The permanent-mute corruption requires the barge-in to occur while a non-final message of a multi-breath response is still playing (i.e. globalId > playingMessage.id + 1); a single-breath (very short) response does not trigger it because nextExpectedId ends up equal to globalId. In default pocket/remote/local modes stopSpeaking does not actually halt the in-flight audio (no AudioContext source reference is retained), so the current utterance plays to its natural end before the zombie loop rolls nextExpectedId back — consistent with the finding's description. The concurrent-processQueue / simultaneous-audio effect is timing-dependent, not guaranteed.

### C2. Scene3D's Canvas uses frameloop="demand", freezing the entire per-frame avatar pipeline (mixer, blink, gaze, lip-sync) in the shipped app whenever the camera isn't being moved

- **Where:** `packages/core/src/components/scene/Scene3D.tsx:240` · avatar-model-pipeline · correctness · **CONFIRMED**
- **Mechanism:** The production Canvas is created with `frameloop="demand"` (Scene3D.tsx:240). In R3F v9 (confirmed @react-three/fiber 9.5.0), demand mode runs the render loop — including every useFrame subscriber — only when `invalidate()` is called. Nothing in the app invalidates continuously: a repo-wide grep for `invalidate`/`frameloop` finds only this line; drei's OrbitControls invalidates only on its own 'change' events during user interaction (node_modules/@react-three/drei/core/OrbitControls.js:41); chat/TTS state lives outside the Canvas so it never triggers commits inside it. All avatar liveliness is driven exclusively by useFrame in AvatarModel.tsx:389-425 (mixer via animationService.actions.update, viseme visemesToRig, emote blink/gaze/ticks) plus drei useAnimations' internal `useFrame(() => mixer.update(delta))`. The service calls that start motion (greet setTimeout at AvatarModel.tsx:360-378, LLM reactions at packages/core/src/services/useAgent.ts:249-250, TTS viseme sequences) mutate plain refs and never invalidate. Crucially, the QA surface that produced the 98-clip WebP gallery is a separate Canvas in apps/web/src/harness/AvatarHarness.tsx (~line 322) that uses the DEFAULT 'always' frameloop, so none of the visual validation exercised the shipped code path.
- **Fails when:** User opens the web app (apps/web/src/App.tsx → Viewport3D → Scene3D): after load settles, the avatar plays no idle loop, never blinks, the greet gesture doesn't run, and when the companion speaks a TTS reply the mouth does not move — unless the user is simultaneously dragging/zooming the OrbitControls camera, during which everything lurches forward by the accumulated clock delta and then freezes again when the drag stops.

## HIGH (12)

### H1. Gaze is completely dead on all GLB avatars (including default Greg) due to a bone-name case mismatch, while the full per-frame vision computation still runs

- **Where:** `packages/core/src/services/emote/modules/gazeService.ts:144` · perf-and-qa-layer · correctness · **CONFIRMED**
- **Mechanism:** For GLB avatars, AvatarModel registers bones by raw node name: `bones[child.name] = child` (AvatarModel.tsx:332). I extracted the node names from apps/web/public/assets/avatars/25-1-3_CI_model_male_Greg.glb: 'Hips, Spine, Spine1, Spine2, Neck, Head, LeftEye, RightEye' — all capitalized. gazeService requires lowercase VRM-humanoid keys: initiateGaze bails on `!state.bones?.neck` (gazeService.ts:102), updateNeckGaze bails the same way (line 144) and on `state.bones.spine2 \|\| state.bones.spine` (line 155), and updateEyeGaze needs `state.vrm?.lookAt` (line 136) which GLB avatars don't have. Only getPlayerVisionState has a capitalized-GLB branch (`state.bones?.Head`, line 235), so the expensive two-eye cone test (lines 256-311, ~30 temp Vector3/Quaternion allocations across up to 4 eyeCanSee calls) executes every frame and its result is then discarded: 'focused' → updateEyeGaze no-op + returnNeckToNeutral no-op (neckOptions.quaternions.default is only ever set inside the unreachable initiateGaze/updateNeckGaze), 'peripheral' → updateNeckGaze early-return.
- **Fails when:** Default avatar Greg (GLB): user walks the camera around the avatar — the head and eyes never track, even though Greg's rig has LeftEye/RightEye/Neck bones that could be driven. Harness triggerGaze() is a silent no-op. Meanwhile every frame burns the full vision-state math for zero visual output. No unit test touches gazeService, so this ships invisibly.
- **Verifier correction:** One minor, non-load-bearing overstatement: the finding's aside that Greg's "LeftEye/RightEye/Neck bones ... could be driven" implies eye tracking is merely mis-wired. In fact, for GLB avatars eye gaze is fundamentally unsupported here — updateEyeGaze (line 136) drives eyes only through the VRM lookAt API, so even with correct lowercase bone names the LeftEye/RightEye bones would not move; only the neck could be driven once its name matched. This does not affect the core finding (gaze is dead + vision math runs per frame), which is fully confirmed. The "~30 allocations" figure is a reasonable upper estimate for the described in-range/above-avatar case; if the camera is below node.y (line 269) or beyond maxDistance (line 274) the function returns before calling eyeCanSee, so per-frame cost is lower in those positions.

### H2. stopSpeaking never stops the currently playing audio buffer, so barge-in cannot interrupt speech in pocket/local/remote TTS modes

- **Where:** `packages/core/src/services/tts/ttsService.ts:438` · llm-reaction-integration · correctness · **CONFIRMED**
- **Mechanism:** playAudioBuffer (ttsService.ts:71-99) creates an AudioContext and AudioBufferSourceNode locally and keeps no reference to them; the promise resolves only via source.onended. stopSpeaking (ttsService.ts:438-457) calls speechSynthesis.cancel() (browser mode only), terminates the generation worker, and clears the queue — it never calls source.stop() or audioContext.close() because it has no handle. The default mode is 'pocket' (ttsConfig.ts:48: VITE_TTS_MODE \|\| 'pocket'), and the production BFF path is 'remote' — both play via playAudioBuffer. So the entire barge-in feature (STT 'stop' at useAgent.ts:289, UI triggerBargein at useAgent.ts:368-377) only prevents FUTURE queued breaths; the utterance currently in the air always plays to its natural end.
- **Fails when:** Avatar is mid-sentence in a long breath (default pocket or remote TTS). User says 'stop' or 'be quiet'. The console logs 'barge-in activated', emotes reset — but the voice keeps talking for the remaining seconds of the current audio buffer. From the user's perspective barge-in simply does not work.

### H3. Barge-in / stopSpeaking never clears the viseme sequence, so the avatar keeps silently mouthing the rest of the interrupted sentence

- **Where:** `packages/core/src/services/useAgent.ts:368` · viseme-lipsync · state-machine · **CONFIRMED**
- **Mechanism:** triggerBargein (useAgent.ts:368-377) and the STT stop-command path (useAgent.ts:288-292) call tts.actions.stopSpeaking() and emotes.actions.onBargeIn(), but never touch the viseme service. The TTS onSpeechEnd handler (useAgent.ts:265-268) also resets only emotes. The generated sequence in visemeStateRef is anchored to absolute performance.now() timestamps (visemesService.ts:92-96), so visemesUpdate (visemesService.ts:127) keeps activating the remaining items until their wall-clock times elapse — nothing anywhere in the repo clears it (grep confirms visemes.actions.reset / resetVisemes has zero call sites). Barge-in is on by default (defaultAppConfig.bargeInEnabled=true, useAgent.ts:186).
- **Fails when:** During a spoken response the user says a stop command (or the app calls triggerBargein): in browser TTS mode the audio halts immediately, but the avatar continues mouth-flapping through the remainder of that sentence's viseme sequence (up to several seconds) with no audio — visibly broken interruption in the core voice-conversation flow.
- **Verifier correction:** Mechanism and severity are accurate. Minor path correction: the viseme service is at packages/core/src/services/visemes/visemesService.ts (the finding writes services/visemesService.ts). All cited line numbers match. The leaked mouth movement lasts until the remaining sequence timestamps elapse OR the next TTS utterance's onSpeechStart calls generateSequence, which overwrites sequence (useAgent.ts:262 / useVisemeService.ts:26) — so in practice bounded by the remainder of the interrupted sentence, consistent with the 'up to several seconds' claim.

### H4. Switching from a VRM avatar to a GLB avatar leaves stale state.vrm and stale 5-key targets, permanently killing lip-sync on the new avatar

- **Where:** `packages/core/src/services/visemes/visemesService.ts:297` · viseme-lipsync · state-machine · **CONFIRMED**
- **Mechanism:** The viseme state lives in a single persistent ref created at app level (useVisemeService.ts:17; App.tsx:60 creates it via useAgent and passes agent.services.visemes down, AvatarModel.tsx:470 only remounts the avatar, not the service). setupVisemeStateForMorphTargets (visemesService.ts:297-305) sets morphs/dictionary/isVRMMode=false but never clears `state.vrm` and never re-creates `state.targets`/`state.dirty`. Two independent mechanisms then break: (1) visemesToRig checks `if (volume.vrm)` FIRST (visemesService.ts:189) and routes all application to the previous, unmounted VRM's expressionManager — the new GLB's morphs are never touched; (2) after a 5-expression VRM, `state.targets` is still the 5-key {aa,ee,ih,oh,ou} object (set at visemesService.ts:279), so visemesUpdate's guard `mappedKey in volume.targets` (visemesService.ts:169-170) silently drops every `viseme_*` write. The harness diagnostic `vrmExpressions()` (apps/web/src/harness/AvatarHarness.tsx:272) reads `visemes.state.viseme.vrm` and reports the stale VRM as if it were the current avatar. The capture gallery never caught this because e2e/capture/gen-webp.mjs:83 reloads harness.html per avatar instead of switching in-session.
- **Fails when:** User selects Yuki (VRM), then switches to Greg (GLB) in the same session and sends a chat message: TTS audio plays but Greg's mouth never moves for the rest of the session (until a full remount/page reload). Same for harness sessions that call __harness.selectAvatar('Yuki') then selectAvatar('Greg') then speak(...).
- **Verifier correction:** Both cited mechanisms are correct. Minor scope refinement: mechanism (1) (stale state.vrm routing visemesToRig into the unmounted VRM's expressionManager) is sufficient on its own and does not require the prior VRM to have been in 5-expression mode — it breaks GLB lip-sync after loading any VRM in the session. Mechanism (2) (stale 5-key state.targets dropping viseme_* writes in visemesUpdate) is a genuine second, independent defect that additionally applies when the prior VRM was 5-expression mode.

### H5. resetEmoteState / barge-in clears state.targets without zeroing previously-driven ARKit morphs, freezing the GLB face at its last expression

- **Where:** `packages/core/src/services/emote/emoteService.ts:61` · emote-face-system · state-machine · **CONFIRMED**
- **Mechanism:** resetEmoteState sets state.targets = {} (line 61), then writes zeros only for the nine VRM_EXPRESSIONS names (91-95) plus neutral/eyesLookDown. applyEmoteStateToMorphTargets (294-314) only writes morph influences for keys PRESENT in state.targets, and the GLB emote dictionary (AvatarModel.tsx:312-327) contains only real morph names like mouthFrownLeft/browDownLeft — the VRM names written by the reset resolve to nothing. So any ARKit influence set before the reset (e.g. mouthFrownLeft 0.8 from 'angry') is simply never written again and the mesh keeps its last value indefinitely. Reset is a main-flow operation: TTS onSpeechEnd → emotes.actions.reset() (useAgent.ts:265-268) and barge-in → handleBargeIn → resetEmoteState (emoteService.ts:267-270, useAgent.ts:288-292).
- **Fails when:** User says 'stop' while the GLB avatar is mid-angry performance → handleBargeIn → resetEmoteState → state says 'neutral' but the mesh keeps frown/brow-down/jaw-forward influences frozen at their interrupted values; the avatar wears a stuck angry face until some future emotion happens to write those exact keys again.
- **Verifier correction:** Two refinements, neither of which changes the verdict. (1) angry's mouthFrownLeft is 0.7, not 0.8 (moodConfigurations.ts:33); 0.8 is sad's value — but all the cited frozen morphs (frown/brow-down/jaw-forward) are genuinely in angry's baseline. (2) The bug is broader than barge-in: onSpeechEnd fires emotes.actions.reset() after every utterance (useAgent.ts:265-268), and the performance relaxation window is min 2s (emoteService.ts:258-260), so any TTS shorter than ~2s ends mid-relaxation and freezes the partially-relaxed face on the default GLB avatar even without a 'stop' command — making this a routine occurrence, not an edge case. Also note a subsequent 'happy' emote will NOT clear the frozen frown (happy's baseline lacks those keys); only a later emotion whose baseline includes the exact frozen keys (e.g. another angry/sad) clears it, matching the finding's 'those exact keys' phrasing.

### H6. applyEmotion never clears the previous emotion's baseline targets, leaving facial residue that persists across emotion changes

- **Where:** `packages/core/src/services/emote/emoteService.ts:124` · emote-face-system · correctness · **CONFIRMED**
- **Mechanism:** applyEmotionInternal (emoteService.ts:110-134) writes the new mood's baseline keys into state.targets (117-121) and then resets ONLY the six VRM preset names ['happy','angry','sad','surprised','relaxed','neutral'] (124-125). It never zeroes the ARKit baseline keys of the PREVIOUS emotion. moodConfigurations baselines are largely disjoint per emotion (e.g. disgust sets noseSneerLeft:1, eyeSquintLeft:1, mouthShrugUpper:0.8 — moodConfigurations.ts:91-115 — none of which are in happy's baseline, moodConfigurations.ts:15-25). updateEmotionRelaxation (226-236) also only iterates currentMoodConfig.baseline keys, so the stale keys are never decayed either; applyEmoteStateToMorphTargets (302-311) keeps re-writing the stale values to the mesh every frame. Emotion changes are common: useAgent.ts:233-251 calls emotes.actions.performAction per LLM breath with detectEmotionFromText per-breath, so multi-sentence responses routinely switch emotions mid-utterance. The gallery face-capture flow (e2e/capture/gen-webp.mjs:150-170) also runs happy→sad→angry→fear→love sequentially on the same page with no reset, so later emote WebPs inherit earlier baselines.
- **Fails when:** GLB avatar (default 'Greg'): LLM breath 1 'That's awful, I'm sorry' → disgust/sad baseline (noseSneer 1, eyeSquint 1, mouthPucker 0.5); breath 2 'But here's the great news!' → applyEmotion('happy') sets mouthSmile 0.6 but the sneer/squint/pucker morphs stay at full strength for the rest of the utterance — the avatar smiles through a snarling face until the speech-end reset.
- **Verifier correction:** Fully confirmed; one trivial attribution nit that does not affect the outcome: mouthPucker:0.5 belongs to sad's baseline (moodConfigurations.ts:58), not disgust's — disgust contributes noseSneerLeft:1 / eyeSquintLeft:1 / mouthShrugUpper:0.8. Since breath 1 resolves to exactly one of disgust/sad, the specific residual keys depend on which, but residue (non-happy ARKit keys surviving into the happy pose) occurs either way.

- **Where:** `packages/core/src/services/emote/modules/gazeService.ts:104` · emote-face-system · correctness · **CONFIRMED**
- **Mechanism:** For GLB avatars, bones are registered under their raw names — bones[child.name] (AvatarModel.tsx:332) — which for RPM rigs are capitalized ('Neck', 'Spine2', 'Head'; gazeService itself reads the capitalized `state.bones?.Head` at line 237 for the GLB vision path). But initiateGaze early-returns on `!state.bones?.neck` (line 104), updateNeckGaze requires `state.bones?.neck` (144) and `state.bones.spine2 \|\| state.bones.spine` (155) — all lowercase, only present for VRM (AvatarModel.tsx:294-298 uses humanoid keys). Consequences on every GLB avatar including the default: initiateGaze never runs → gazeState.gazeTime never set → isActiveFocus always false; updateNeckGaze no-ops; updateEyeGaze requires state.vrm.lookAt (135-139) which GLB lacks. The gallery 'eyes' captures mask this by driving ARKit morphs directly with services disabled (e2e/capture/gen-webp.mjs:172-206).
- **Fails when:** Default avatar Greg (GLB): user walks in front of the companion — no eye contact, no head turn, ever. - **Verifier correction:** All core claims hold. One negligible imprecision: the animation catalog contains no M_* clips — only the F_* feminine set exists (animationClips.ts) — so the head/neck track stripping in practice affects only female GLB avatars, not "all F_*/M_* clips". The code does test /^[FM]_/, and Greg's clips are unprefixed so his head still animates from idle (his failure is purely the missing gaze, which the finding states correctly). This does not weaken any of the stated failure scenarios.

### H9. Switching from a VRM avatar to a GLB avatar permanently kills lip-sync and blinking on the GLB: setupVisemeStateForMorphTargets/setupEmoteStateForMorphTargets never clear the stale state.vrm

- **Where:** `packages/core/src/services/visemes/visemesService.ts:189` · avatar-model-pipeline · state-machine · **CONFIRMED**
- **Mechanism:** The viseme/emote services are owned by useAgent and persist across avatar remounts (AvatarModel is remounted via key on model change, AvatarModel.tsx:468-471). When a VRM avatar is selected, setupVisemeStateForVRM sets `state.vrm` (visemesService.ts:267). When the user switches back to a GLB avatar, AvatarModel's GLB branch calls setupForMorphTargets (AvatarModel.tsx:275), but setupVisemeStateForMorphTargets (visemesService.ts:297-305) only sets morphs/dictionary/isVRMMode — it never clears `state.vrm`. visemesToRig then takes the VRM branch first (`if (volume.vrm)`, visemesService.ts:189) and writes all mouth values into the unmounted old VRM's expressionManager; the GLB morph branch (visemesService.ts:224-243) is unreachable. Worse, `volume.targets` remains the 5-key VRM shape while isVRMMode=false, so visemesUpdate's `mappedKey in volume.targets` check (visemesService.ts:169-171) rejects every incoming 'viseme_*' key — no viseme data is even accumulated. The emote service has the identical flaw (setupEmoteStateForMorphTargets, packages/core/src/services/emote/emoteService.ts:336-352): with stale state.vrm, applyBlinkExpression (packages/core/src/services/emote/modules/blinkingService.ts:35-43) writes the VRM 'blink' key instead of eyeBlinkLeft/Right/eyesClosed, which does not exist in the GLB morph dictionary, and updateVRMSystems (emoteService.ts:186-198) keeps updating the dead VRM's lookAt/expressionManager every frame, pinning the whole old VRM scene graph in memory.
- **Fails when:** Default Greg (GLB) lip-syncs fine → user tries Yuki (VRM) → user switches back to Greg (or any GLB avatar): from then on Greg's mouth never moves during TTS and he never blinks, until a full page reload. Every subsequently selected GLB avatar is equally dead-faced.
- **Verifier correction:** Confirmed as written. One clarifying nuance: the specific sub-claim that "no viseme data is even accumulated" (the volume.targets rejection at visemesService.ts:169-171) holds only when the intermediate VRM was a 5-expression VRM that set isVRMMode=true and swapped targets to the 5-key VRM shape — which is precisely the Yuki case in the stated scenario. For a hypothetical full-viseme VRM (isVRMMode stays false, targets stay 14-key), accumulation would still work but lip-sync would remain dead anyway because visemesToRig still takes the stale `volume.vrm` branch. Either way the headline defect (dead lip-sync + no blinking on any GLB selected after any VRM, until page reload) is correct.

### H11. AnimationMixer is updated twice per frame (drei useAnimations + updateAnimation), so all avatar animation plays at 2x speed

- **Where:** `packages/core/src/services/animation/animationService.ts:177` · mixer-state-machine · correctness · **CONFIRMED**
- **Mechanism:** updateAnimation calls `state.mixer.update(delta)` (animationService.ts:177). But the mixer passed into setup is drei's: AvatarModel.tsx:225 gets `{ actions, mixer }` from `useAnimations(...)` and passes it to `animationService.actions.setup(...)` (AvatarModel.tsx:239). drei's useAnimations registers its own `useFrame((state, delta) => mixer.update(delta))` (node_modules/@react-three/drei/core/useAnimations.js:35, v10.7.7), which runs unconditionally for the same mixer instance.
